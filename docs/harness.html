1什么是 Harness Engineering？

Harness Engineering（驾驭工程 / 缰绳工程）是 2025-2026 年 AI Agent 开发领域兴起的一门新学科。

一句话解释：为 AI 智能体设计环境、约束和反馈回路，让它从"能聊天"变成"能干活"。

视频开头讲了一个真实案例：一个团队用了最强的模型，迭代了上百版提示词，但 Agent 的任务成功率始终低于 70%。后来他们不再纠结于提示词本身，转而构建了一套结构化的驾驭系统，成功率大幅提升。

核心认知：问题不在模型，而在你如何"驾驭"模型。

2核心公式：Agent = Model + Harness

Agent = Model + Harness
Model

大语言模型

GPT、Claude 等提供原始智能。就像马的体力和智力。

Harness

驾驭系统

围绕模型构建的环境、工具、约束、反馈。就像缰绳、马鞍、跑道、训练方法。

6 倍性能提升：Harness 架构可以让同一个模型的性能提升 6 倍。这不是夸张，多个团队已验证过。

3六层架构总览

Harness Engineering 的核心是六层架构，从内到外逐层构建：

L6 约束与护栏 安全边界、权限控制、领域隔离
║
L5 反馈与评估 测试、CI/CD、代码审查、自修正
║
L4 记忆与上下文 CLAUDE.md、AGENTS.md、知识库
║
L3 工作流编排 SOP、任务分解、多智能体协调
║
L2 工具与执行 文件系统、Bash 沙箱、MCP、搜索
║
L1 信息边界 上下文范围、项目结构、文档
构建原则：从 L1 开始逐层向外搭建，每一层都建立在前一层的基础上。

4L1：信息边界层

定义

控制 Agent 能看到什么信息。就像给 Agent 一张项目地图，告诉它"这里有什么，别的地方别去"。

为什么重要

没有信息边界的 Agent 就像把人扔进图书馆但不给目录——它会浪费时间在不相关的文件上，或者遗漏关键上下文。

实操方法

4.1 项目上下文文件

在项目根目录创建 CLAUDE.md，告诉 Agent 项目的基本结构：

# Project Context
This repo is a personal knowledge base.

## How It Works
- Each top-level folder = one topic/module
- Notes are written in Markdown
- Static demo pages go inside a docs/ subfolder

4.2 模块化上下文

对于大型项目，每个模块放自己的上下文文件：

project/
├── CLAUDE.md              # 全局项目上下文
├── src/
│   ├── api/
│   │   └── CLAUDE.md      # API 模块上下文
│   ├── frontend/
│   │   └── CLAUDE.md      # 前端模块上下文
│   └── database/
│       └── CLAUDE.md      # 数据库模块上下文

5L2：工具与执行层

定义

Agent 能使用哪些工具和执行环境。信息边界告诉 Agent"有什么"，工具层告诉 Agent"能做什么"。

工具执行环境
文件系统 Bash 沙箱 Web 搜索 MCP

核心工具

5.1 文件系统 — 结构化访问

project/
├── src/           # 源码 — Agent 可以修改
├── tests/         # 测试 — Agent 应该更新
├── docs/          # 文档 — Agent 可以补充
├── .claude/       # Agent 配置 — Agent 可以调整
└── secrets.env    # 密钥 — Agent 只能读取

5.2 MCP（Model Context Protocol）

MCP 是 Agent 连接外部系统的标准化协议：

// MCP Server 配置示例
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"]
    },
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/workspace"]
    }
  }
}

6L3：工作流编排层

定义

Agent 如何工作——任务分解、执行步骤、多智能体协调。从"单步操作"到"流程驱动"的关键层。

6.1 SOP（标准操作流程）

为常见任务定义标准流程：

阅读 CLAUDE.md 了解项目结构
↓
探索相关模块的代码
↓
设计实现方案（列出步骤）
↓
编写代码
↓
运行测试
↓
更新文档并提交

6.2 多智能体编排

协调者 Agent
↓ 分解任务
前端 Agent 后端 Agent 测试 Agent
↓ 合并结果 → 审查 → 输出

7L4：记忆与上下文层

定义

Agent 如何记住之前的工作和学习成果。没有记忆的 Agent 每次都是全新的开始。

短期

会话记忆

对话历史、当前任务、工具调用、中间状态。

长期

持久化记忆

项目知识（CLAUDE.md）、用户偏好（memory/）、反馈记录、经验教训。

记忆目录结构

.claude/memory/
├── MEMORY.md          # 记忆索引
├── user_role.md       # 用户信息
├── feedback_*.md      # 反馈记录
├── project_*.md       # 项目状态
└── reference_*.md     # 外部资源引用

8L5：反馈与评估层

定义

Agent 如何知道自己做得对不对。从"盲盒输出"到"可控质量"的关键。

反馈回路

任务输入 → Agent 执行 → 评估
↠
自修正 ← 反馈结果

8.1 自动化测试循环

Agent 修改代码
↓
运行单元测试
↓
如果失败：分析错误 → 修复 → 重新测试
↓
如果通过：运行集成测试 → 提交

8.2 代码审查循环

// Agent 完成修改 → 触发审查
审查 Agent 检查：
  - 是否符合项目约定 (CLAUDE.md)
  - 是否有安全漏洞
  - 是否引入不必要的复杂度
  - 测试是否覆盖

9L6：约束与护栏层

定义

Agent 不能做什么。最后一道防线，确保安全性和可控性。

权限约束

能读不能改

不能删文件、不能执行 rm、不能推送主分支。

领域约束

领域隔离

只负责前端、不碰后端、不碰数据库、不碰基础设施。

权限控制示例

{
  "permissions": {
    "Read":         "auto",
    "Edit":         "auto",
    "Bash":         "prompt",
    "Bash:npm test": "auto",
    "Bash:git push": "deny",
    "Bash:rm *":     "deny"
  }
}

10渐进式学习路径

从简单到复杂，六个 Level 逐步构建 Harness 能力。

Level目标预计时间检查点
1
单文件修改		让 Agent 正确修改一个文件30 分钟Agent 能正确定位文件且不引入 Bug
2
多文件协调		在多个文件间正确修改1-2 小时理解文件间依赖关系，按正确顺序修改
3
工作流编排		定义 SOP，按流程执行半天能分解大任务，Hooks 在正确节点触发
4
记忆系统		从历史经验中学习1 天不会重复已知错误，应用用户偏好
5
自动反馈		自我验证和修正1-2 天能识别测试失败并自动修复
6
完整 Harness		生产级六层系统1 周所有层协同，约束不被绕过
建议：从 Level 1 开始，每通过一个检查点再进入下一层。不要跳级。

11企业实战场景

场景一：日常开发辅助

背景：开发团队 5 人，日常有大量 CRUD 功能和 API 端点需要实现。

层配置
L1CLAUDE.md 包含项目架构、API 规范、数据库约定
L2文件系统读写 + npm 工具 + 本地测试环境
L3SOP = "读文档 → 设计 → 编码 → 测试 → 提交"
L4记忆团队编码约定和历史踩坑记录
L5每次修改后运行单元测试 + lint + 类型检查
L6禁止修改基础设施配置，禁止推送主分支
效果：简单功能开发时间从 2 小时缩短到 20 分钟，Agent 成功率从 60% 提升到 95%。

场景二：Code Review 自动化

背景：PR 量大，人工审查不过来，需要 Agent 自动做第一轮审查。

层配置
L1CLAUDE.md 定义代码规范、架构约定
L2git diff 读取变更 + 静态分析工具
L3SOP = "读取 PR → 分析变更 → 检查规范 → 检查安全 → 生成报告"
L4记忆团队的代码审查偏好和历史问题
L5生成审查报告，标记需要人工关注的点
L6只能评论，不能直接合并或关闭 PR

场景三：多 Agent 协作开发

背景：一个全栈功能需要前端、后端、测试、文档同时开发。

协调者 Agent (L3)
前端 Agent 后端 Agent 测试 Agent 文档 Agent
↓
审查 Agent (L5)
↓ 通过 → 合并 / 不通过 → 返回修改

12常见问题与排错

Agent 总是忽略我的约束怎么办？
1) 检查 CLAUDE.md 是否在正确位置；2) 约束描述是否清晰明确（避免"尽量"等模糊用词）；3) 在 L6 层面添加硬约束（权限配置），而非仅依赖文本描述。
Agent 的修改通过了测试但有 Bug 怎么办？
这是 L5 反馈层不够强的信号。补充缺失测试用例、添加集成测试、引入静态分析工具、在 CLAUDE.md 中记录常见 Bug 模式。
多 Agent 协作时互相覆盖修改怎么办？
L6：严格划分每个 Agent 的修改范围。L3：协调者控制执行顺序，避免并行冲突。L2：使用 git 分支隔离，最后统一合并。
如何衡量 Harness 的效果？
指标目标值
任务成功率> 90%
平均修复次数< 2 次
上下文准确率> 95%
约束遵守率100%
总结：Harness Engineering 的核心思想是——不要纠结于让模型更聪明，而是构建一个让模型能可靠工作的系统。六层架构从信息边界到约束护栏，每一层都在增加 Agent 的可靠性。从 Level 1 开始，逐层构建。
